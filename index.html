case study 01 · solo build · 28–31 aug 2026

Label Lens — decode what's actually in your food

role everything stack Python stdlib · Groq vision model · phone web UI repo sample reports changelog with evidence
the customer

An Indian shopper in a kirana aisle holding a packet that says "Flavour Enhancers (627, 631), Caramel (150d), Emulsifier (471)". Six seconds of attention, no way to decode a single code, and the top search result calls citric acid dangerous. The information exists at EFSA, the FDA and the EU register. It is not reachable in six seconds.

the scoping

The model gets one job: transcribe. Identity, regulatory tier and citations come from a 49-entry database sourced line by line to the regulators, so a tier can only be wrong if the database is wrong. It cannot be hallucinated. A verifier then drops any code the transcription cannot support.

I refused to build the obvious next feature, a "safe products" recommender. Endorsing named products is a stronger claim than the evidence carries. It is still not built.

the eval

Thirteen real packets from my kitchen, photographed on a phone. Ground truth verified by hand against each physical label, which caught three missing codes and one wrong subtype in the model-drafted version. Same scorer and same model on both sides. The baseline is the one-shot "list the harmful chemicals" prompt everyone writes first.

the finding

The first full eval scored my agent worse than the baseline. Under deadline pressure the tempting move was to switch models. The per-task records said otherwise: five additive-free products were being scored zero for an honest empty answer, grouped codes like "(627, 631)" resolved to the first only, and subtype notation like "170(i)" could never match. Three fixes to my measurement code, zero to the model. The ruler was broken.

the outcome
0.812 → 0.931mean extraction F1
8 → 9 / 13labels extracted perfectly
1 → 0crashed scans
0regressions vs baseline
$0.038cost for all 13 labels

Invented codes fell from 6 to 5, not the 3× the interim number suggested. I published the wrong interim figure and the corrected one side by side, with the reason: rescoring old output is not the same as re-running the fixed pipeline live.

production notes

Real-device testing found what localhost never will: a phone hotspot that was IPv6-only, a Cloudflare 403 caused by Python's default User-Agent, 4032-pixel uploads tripping rate limits (fixed with browser-side downscaling at identical extraction quality), and truncated request bodies from a flaky link. Every failure path saves its evidence. The reproducibility gate was rewritten to fail loudly when a run has no credentials, after it once reported PASSED on a run that reproduced nothing.

what's next

The remaining errors are vision misreads (627 transcribed as 621) that verification structurally cannot catch, because it checks the model against its own reading. Next build: a second independent transcription pass with disagreement flagging, so a misread becomes a visible conflict instead of a confident wrong answer.

case study 02 · jul–sep 2026 · 11 codebases · python, typescript, go

Open source, upstream

The nearest thing to a forward deployment you can do alone: pick a production codebase you have never read, find the bug, reproduce it on main, fix it the way the maintainers would, and negotiate the change through review with the people who own the code.

Six that show the pattern.

typeshed #16244
A CI crash that only happened on some runnersDaily stubtest died with exit −4 and no output, but passed locally and on macOS. Timing data from three consecutive runs (25 s fresh compile against 6–9 s cache hits) showed a pip wheel compiled with -march=native on one host being restored on another CPU. Fix: build without it, and revert the earlier darwin-only workaround.
astroid #3238
A wrong signature in the object model, three years of false positivesThe fallback __new__ was declared as (self, cls), but __new__ has no implicit parameter. Every call through ssl, array and datetime produced spurious argument errors in pylint. Fixed with tests; closed a pylint issue open since 2023.
pylint #11307
Ten checkers rejecting valid stdlib codeThe invalid-*-returned family compared class names to builtin names, so any subclass of str, int or dict was rejected. Switched to a real subtype check, which also closed a loophole for unrelated classes merely named "str".
litestream #1452 · Go
Two config entries, one directory, a silent raceDuplicate database paths started two managers on one metadata directory and raced on temp files. Added cross-entry validation at config load with an error naming both entries. Reproduced on main first; approved by the project's author.
corsair #854, #855 · TypeScript
Webhook verifiers that fail closedConstant-time comparison for the Outlook client state instead of ===; the Figma verifier now errors when its passcode is missing instead of accepting everything. Unit tests for match, mismatch and missing.
redash #7809 · in review
Dynamic date parameters, resolved where scheduled queries can use themMoved parameter resolution to the backend so scheduled refreshes stop running with stale dates; 313 lines across the query model and the refresh path, with the stored query hash refreshed before enqueueing. A sibling layout-migration fix (#7791) was approved after two rounds of maintainer review.

Every PR body reads like a hand-off note: reproduction on main, what changed, what was deliberately left out, and the evidence. Where a coding agent helped, the PR says so. The agent writes fast; I own what ships.

Harbor task
dynamo-log-report

A Terminal-Bench 2 task for evaluating coding agents: parse an Apache access log into a JSON report. Dockerfile pinned by digest, an oracle solution, and a pytest verifier that emits a reward. Oracle scores 1.0, a no-op scores 0.0, so the task cannot be passed by accident.

Why it matters for deployment work: evals are the steering wheel. I have written rubrics that eleven people could apply consistently, and I have watched a rubric that could not score an honest empty answer make a working system look broken.

how i work with customers

Four habits, each with the receipt.

Discovery before code.

At Zoho and at TCS the job was the same: sit with the people who own the problem, find the sentence they actually mean, write it down, then build to that sentence and not the ticket.

Always be scoping.

Label Lens could have shipped a "safe products" recommender. The evidence could not carry the claim, so it does not exist. Saying no early is cheaper than a retraction.

Measure, or say you can't.

When the eval said my agent was worse, I read the failures before touching the model. I publish the interim number and the corrected number together, with the reason.

Leave it runnable.

Every PR is a hand-off note a stranger can act on. Every squad guideline was rewritten until the questions stopped. The goal is a customer who does not need me next quarter.
